# Prompt for Claude — BarangGabay: upgrade the voice reader to real AI voices in English, Filipino, and Manobo

Paste this into Claude Code, working inside the project folder.

## What exists now, and what's changing

You already built `app/views/shared/_voice-reader.php`, `_voice-preview.php`, and `App\Services\SpokenText`. That implementation:

- uses the **browser's** `speechSynthesis` engine, so the voice is whatever the device happens to have installed — different on every phone, often missing `fil-PH` entirely;
- returns `null` from `SpokenText::speechLang()` for Manobo (`msm`) and deliberately never synthesises Manobo, playing only the human-recorded `audio_manobo_path`;
- follows the header's FIL / EN / MN switch, with no language choice inside the player itself.

**This is a deliberate change of direction on all three points.** The goal now is a real AI narrator voice, generated server-side, available in **all three languages on every post**, selectable from inside the player. Keep the good parts — `SpokenText`'s script building, the lead/tail structure, the truncation notice, the shared-partial design — and change the audio source and the language handling.

Do not rewrite these files from scratch. Refactor what's there.

## 1. Server-side AI voices, cached per post per language

Browser speech goes from being the engine to being the *fallback*. The primary source becomes an MP3 generated by a real TTS provider.

- Use **Google Cloud Text-to-Speech** (`fil-PH` Wavenet/Neural2 voices, `en-US`/`en-GB` for English) or **Azure Speech** (`fil-PH-BlessicaNeural`, `fil-PH-AngeloNeural`). Both have free monthly tiers far larger than a barangay's posting volume. Put the key and provider choice in `.env` plus a config file next to `config/ai.php`. **Anthropic has no TTS API** — do not try to route this through the existing Anthropic key.
- **Generate once per post per language at publish time, never per page view.** A resident pressing Listen must hit a cached file. Generating on playback is how a free tier evaporates and how a slow barangay connection turns a button into a 6-second wait.
- Cache in a new table rather than adding columns to three tables:
  `post_audio (id, content_type ENUM('announcement','event','ordinance'), content_id, locale ENUM('en','fil','msm'), source ENUM('ai','human'), audio_path, voice_name, text_hash, duration_seconds, generated_at, generated_by)`, unique on `(content_type, content_id, locale, source)`.
- `text_hash` is a hash of the exact spoken script (`SpokenText::script()` output). When staff edit a post, the hash stops matching and the audio is marked **stale** and queued for regeneration — it must not keep serving the old wording.
- Update **both** `schema.sql` and a new numbered file in `database/migrations/`, per `runPendingMigrations()` in `config/database.php`. Delete the audio files when the post is deleted.
- Keep browser `speechSynthesis` as the fallback when no MP3 exists yet or generation failed, so the feature never fully disappears.

## 2. Three languages inside the player

The player gets an **EN / FIL / MN** selector, defaulting to the header's current locale so the two never contradict each other on first load. A resident who is reading in Filipino but wants to *listen* in Manobo (or play it for an elder) can switch just the audio.

Which text gets spoken per language — this is the part that must be exactly right:

- **EN** → the English translation fields. If a post has no English translation yet, don't invent one at speech time; show the language as unavailable.
- **FIL** → the Filipino original (the Quill body, HTML-stripped, as `SpokenText` already handles).
- **MN** → the Manobo translation text.

**Manobo audio depends on Manobo text existing first.** Your screenshot currently shows "Manobo translation is not available right now" — as long as that's failing, there is nothing for any voice to read. Check why the translation path (the Claude translator + the curated dictionary at `/admin/manobo`) is returning empty before wiring Manobo audio, and make the admin flow generate and store the Manobo translation at publish time rather than on-demand per resident.

## 3. Manobo voice — the honest version

The earlier rule ("never point a Filipino voice at Manobo text") is now relaxed, but with conditions, because the underlying fact hasn't changed: **no provider has an Agusan Manobo voice.**

What actually happens if a `fil-PH` voice reads Manobo text: Manobo uses the same Latin, largely phonemic orthography as Filipino, and the two share most of their vowel and consonant inventory — so the output is *roughly intelligible* rather than nonsense. What it gets wrong: the Manobo schwa (usually written ⟨e⟩) comes out as Filipino /ɛ/, stress and phrasing follow Filipino rules, and glottal stops land in the wrong places. A Manobo speaker will understand much of it and will also immediately hear that it is not a Manobo speaker.

So the priority order for MN audio is:

1. **Human recording** (`audio_manobo_path`) if staff uploaded one — always preferred, always used first. Label it "Recorded by a community member."
2. **AI approximation** — a Filipino voice reading the Manobo text — when no recording exists. It must be **visibly labeled** as an AI approximation using a Filipino voice, in all three UI languages, right next to the play button. Not a footnote.
3. If neither exists, say so plainly and offer the Filipino reading instead (the current behaviour).

Make it easy for staff to replace an AI approximation with a real recording later, and show in the admin list which posts are still relying on the approximation, so the barangay can work through them. If a Manobo speaker on the barangay staff or in the community reviews these, take that feedback over the approximation every time.
